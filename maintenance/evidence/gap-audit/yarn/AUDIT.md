# Yarn discontinuity audit

This audit covers all 2,680 Yarn fixture/version points in `maintenance/evidence/compatibility-policy-update/report.json`: 335 published versions across eight fixtures. `coverage.json` assigns every point a cause, original outcome, recommended outcome after the new probes, original row/evidence IDs, and new row IDs. `point-evidence.json` links every historical attempt to its raw row, log, runtime, and failure signature. No historical row, exclusion, or observation was edited.

The initial inventory has **no internal unsupported Yarn run bracketed by supported releases**. Its two internal unknown points are Classic `1.22.12` and Modern v8 `4.9.1`. The latter is already inside the shipped v8 range; it is an evidence uncertainty rather than an excluded interval in that range.

## Corrections established by new execution

| Point | Root cause and evidence | Disposition |
| --- | --- | --- |
| Classic `1.22.12` | The official npm tarball is an unbundled distribution. npm bootstrap ran inside the tool's own package root and attempted to resolve its omitted development dependencies, producing `ERESOLVE` for development ESLint peers. The same official executable passes `--frozen-lockfile` on Node 16.11.1 after preparing only its runtime dependencies; bytes stay unchanged and the contradictory manifest control is rejected. All seven Modern fixtures are explicitly rejected by the same verified executable. | Import the new standard rows. The internal unknown is supported for Classic, unsupported for the Modern formats. |
| Modern v5 `3.1.0-rc.11`, `3.1.0-rc.12` | Both failed during tar extraction with `ERR_STREAM_PREMATURE_CLOSE` on Node 24. Both pass `--immutable`, unchanged fixture bytes, installed package verification, and the contradictory control on Node 16.11.1. `rc.12` also fails on Node 17.0.1, proving that choosing the newest historical Node does not automatically remove this problem. | Import the two positive rows. The v5 prerelease lower boundary can start at `3.1.0-rc.11`. |
| Modern v4, 25 unknown prereleases: `3.0.0-rc.1`–`rc.13`, `3.0.1-rc.1`–`rc.2`, `3.1.0-rc.1`–`rc.10` | They encounter the same stream failure under Node 24, but every one was rerun under Node 16.11.1. All install the correct dependency and then change cache generation 7 to 8 and its checksum. The metadata format stays 4. | Import the 25 negative rows: they are frozen-install incompatible because of a deliberate cache migration. Do not excuse them under the stream-bug review. |

The upstream Node 17 defect and its precise stream lifecycle fix are documented in [Yarn #3597](https://github.com/yarnpkg/berry/issues/3597) and [Yarn #3610](https://github.com/yarnpkg/berry/pull/3610). `known-bug-candidates.json` contains one optional review for exactly four existing **v5 rc.11/rc.12** observations, with `observationFingerprint()` hashes. This is an annotation of independently proven compatibility; the new positive observations already establish that compatibility without rewriting the failures. It does not include v4 or any neighboring release.

The package distribution incident is independently recorded in [Classic #8695](https://github.com/yarnpkg/yarn/issues/8695). The bootstrap diagnosis is also consistent with [npm's omit documentation](https://docs.npmjs.com/cli/v11/using-npm/config/#omit): omitted dependency types still participate in resolution.

## All format and cache boundaries

The table distinguishes metadata-format migrations from cache serialization differences. Both can violate the repository's byte-preserving frozen-install contract. Unchanged `__metadata.version` alone is insufficient to waive a failed experiment.

| Fixture | Audited boundaries and exclusions | Classification |
| --- | --- | --- |
| Classic v1 | Confirmed support starts at the first currently conclusive `0.21.0` and continues through `1.22.22`; the `1.22.12` point is now positively measured. Modern Yarn rejects this input under `--immutable` because it needs migration. | Real frozen migration boundary. There remains no confirmed unsupported-to-supported **stable lower boundary**, so the compiler deliberately emits no Classic rule. Earlier unknown versions must not be assumed unsupported. |
| Modern v4, cache key 7 | `2.0.0-rc.34` through `2.2.2` accept the graph but rewrite cache key/checksum; `2.2.2` was independently reproduced with key 7 → 6. `2.3.0` through `2.4.3` preserve the fixture. From `3.0.0-rc.1` through `3.1.0-rc.10`, key 7 → 8 changes the frozen bytes. `3.1.0-rc.11` changes metadata version 4 → 5. Earlier CLI versions either reject the metadata or remain unknown for the explicitly listed checksum/provisioning reasons. | Deliberate cache migration at both stable ends of the shipped v4 interval; true metadata migration at `3.1.0-rc.11`. Retain `>=2.3.0 <3.0.0`. |
| Modern v5 | Metadata version 5 starts at `3.1.0-rc.11`, now measured on a working Node runtime. The fixture remains supported through `3.2.0-rc.11`; `3.2.0-rc.12` requires version 6. The immediately preceding `3.1.0-rc.10` was rerun on the same Node 16.11.1 and explicitly rejects v5. | Node stream bug accounts for the two missing lower prereleases. | Modern v6 | `3.2.0-rc.11` would change format 6 → 5. `3.2.0-rc.12` passes both the fixture and control. `4.0.0-rc.1` changes format 6 → 7 and normalizes a dependency descriptor to `npm:7.0.0`. | Real format transitions, independently paired with v5 at `3.2.0-rc.12`. |
| Modern v7, cache key 9 | All 45 published `4.0.0-rc.1`–`rc.45` points pass. `rc.46` still uses format 7 but changes cache key 9 → 10 and the archive checksum; this exact rewrite was independently reproduced. `rc.47` changes metadata version 7 → 8. | Deliberate cache migration at `rc.46`, then real format migration. The compiler deliberately retains `null` for this **prerelease-only** supported island under the existing strict proof contract: a partial restriction could exclude stable versions whose behavior is unknown. Omitted formats infer as `*`; the 45 supporting experiments remain in the report. This audit does not change that policy. |
| Modern v8, cache key 10c0 and explicit checksum key | Format 8 exists in `4.0.0-rc.47`, but all ten published versions from `rc.47` through `4.0.2` strip the fixture's `10c0/` checksum prefix during immutable validation. | Modern v10 | `4.14.1` would change format 10 → 9; `4.15.0` passes v10 and rejects v9. The current catalog ends at `4.18.0`, which is supported. | Real lower format transition; no measured upper failure in this catalog. |

Official source snapshots with SHA256 receipts are under `sources/`. They include `Project.ts` lockfile-version constants and `Cache.ts` generation constants for the relevant releases. Examples: [v5 source](https://raw.githubusercontent.com/yarnpkg/berry/@yarnpkg/cli/3.1.0-rc.11/packages/yarnpkg-core/sources/Project.ts), [v6 source](https://raw.githubusercontent.com/yarnpkg/berry/@yarnpkg/cli/3.2.0-rc.12/packages/yarnpkg-core/sources/Project.ts), [rc.46 cache](https://raw.githubusercontent.com/yarnpkg/berry/@yarnpkg/cli/4.0.0-rc.46/packages/yarnpkg-core/sources/Cache.ts), [v9 source](https://raw.githubusercontent.com/yarnpkg/berry/@yarnpkg/cli/4.14.0/packages/yarnpkg-core/sources/Project.ts), and [v10 source](https://raw.githubusercontent.com/yarnpkg/berry/@yarnpkg/cli/4.15.0/packages/yarnpkg-core/sources/Project.ts).

[Yarn PR #6083](https://github.com/yarnpkg/berry/pull/6083) explains why 4.1.0 always writes checksum cache keys: implicit global keys could corrupt a merged lockfile. Our v8 backward-install failure does **not** reproduce that merge-corruption bug. It demonstrates the intentional old/new serialization difference, so this audit does not turn those ten negatives into known-bug exceptions.

## Remaining unknowns, exhaustively accounted for

After importing the conclusive new rows, 313 point uncertainties remain. This count is over fixture/version pairs, not distinct releases. Every one belongs to one of these seven causes; none is an unexplained internal negative island.

| Cause | Points | Evidence and disposition |
| --- | ---: | --- |
| `0.1.0`–`0.1.3` have no usable CLI declaration in the selected official packages | 32 | Provisioning cannot execute a version-verified manager. No lock-format assertion is justified. |

| Bundles labeled `2.0.0-rc.4` and `rc.5` report different versions | 16 | The official committed bundles report `2.0.0-rc.1` and `rc.4`, respectively. Preserve exact identity checks and the original provision failures. No version alias was inferred from neighbors. |

## Semver presentation

The extra OR clauses for `3.6.0-git.20230603.hash-3c8237cb`, `4.4.1-git.20240825.hash-b2f315f6`, `4.9.1-git.20250411.hash-1908ee79`, and `4.13.0-git.20260303.hash-81f3e15d` opt those published prerelease tuples into ordinary semver matching. They are supported samples inside otherwise continuous stable intervals, not stable compatibility gaps. The v5 `3.2.0-rc.1`–`rc.11` clause similarly represents supported prereleases of the stable upper-bound tuple; `rc.12` is the actual format-6 transition.

## Integration and validation

- `rows/`, `logs/`, and `catalog.json` are standard import inputs. `row-import-manifest.json` proves each row is a byte-identical copy of its immutable probe record. Bootstrap locks and logs are additionally copied to `bootstrap/`; `bootstrap-archive-manifest.json` maps their original receipt paths to durable files without editing records.
- `portable-assets.json` gives the production evidence importer each original asset path's relative archive path and SHA256. It covers the original absolute bootstrap paths and the ordinary relative logs. Import validates these hashes, archives the mapping, and rewrites only the imported observation's asset locations; original row bytes stay unchanged. A regression confirms that prerelease-only support continues to produce `null` under the existing compiler contract.
- `coverage.json` tracks the complete original inventory. Original outcome counts: 229 supported, 2,103 unsupported, 348 unknown. After the conclusive probes: 232 supported, 2,135 unsupported, 313 unknown. These are evidence recommendations; range generation remains the compiler's responsibility.
- `maintenance/bootstrap.ts` now derives a temporary manifest without development dependencies, records original and installation manifests plus SHA256 in the bootstrap receipt, restores the exact original manifest before returning the tool, and separates the preparation policy in its cache key. It retains runtime dependency validation and does not use `--force` or `--legacy-peer-deps`.
- The new offline regression first failed with real npm `ERESOLVE`, then passed. It also includes a nonexistent development dependency, verifies the runtime dependency exists, confirms development packages and lifecycle output are absent, and checks the original manifest and provenance hashes.
- Twenty-five tests covering provisioning, frozen controls, and durable bootstrap archival pass. Targeted ESLint passes. Logs: `bootstrap-regression-red.log`, `bootstrap-regression-green.log`, `bootstrap-verification.log`.
- No production compatibility data, shared known-bug reviews, Git commit, or publish operation was performed by this audit agent. Root integration may import the rows and optional review separately.
