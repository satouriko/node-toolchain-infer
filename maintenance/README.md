# Compatibility maintenance

This directory is a runnable measurement pipeline. Runtime inference reads only the small compiled `data/compatibility.json` (raw observations are not bundled); it does not download tools or execute these scripts. The catalog snapshot in `evidence/catalog.json` is an explicitly supplied maintenance artifact, never a runtime default.

## Reproduce

Use Node 24 for development/generation (ESLint 10's formatter requires a recent Node), pnpm 10.33.0, and a clean checkout. Runtime/frozen-install checks also run under Node 18.20.8 in CI.

```sh
pnpm install --frozen-lockfile
pnpm data:sync --output maintenance/results/catalog.json
pnpm fixtures:generate --catalog maintenance/results/catalog.json
pnpm compat:test --catalog maintenance/results/catalog.json
pnpm compat:test --fixture pnpm-lock-v9 --versions pnpm@8.15.9,pnpm@9.0.0 --catalog maintenance/results/catalog.json
pnpm exec tsx maintenance/compile-compatibility.ts --catalog maintenance/results/catalog.json
pnpm releases:check --incremental --state-dir maintenance/results --max-releases 8
pnpm exec tsx --test test/maintenance*.test.ts test/releases.test.ts
```

The boundary matrix intentionally returns 1 because one requested combination is incompatible. The compiler consumes its evidence; a rejection is a successful boundary experiment, not a passing installation. Baseline `compat:test` returns status for the requested combinations only, preserving all historical observations in the file.

`--fixture` selects one recipe. `--node 18.20.8` explicitly provisions that official Node release after checking manager engines. `--versions` accepts comma-separated exact stable `manager@version` pairs. Use an official full catalog to compile boundaries; a reduced test catalog cannot prove adjacency. The full captured catalog includes official URL, fetch timestamp, content hash and release metadata. No global installs are used. Registry distributions are downloaded from the official npm registry, checked against their strongest SRI digest and extracted into a temporary directory. Historical Yarn releases absent from `@yarnpkg/cli-dist` use the official `@yarnpkg/cli` metadata and Git tags. Their standalone bundle URL is pinned to a full commit; byte length, computed SHA-512, metadata source and actual `--version` output are recorded separately from registry SRI. `evidence/yarn-distributions/` retains these source and verification receipts. The invoked binary's version is checked. Host Node is used when its exact version satisfies declared engines; otherwise a compatible exact official Node release is downloaded and checked against Node SHASUMS256. Host Node receipts hash the executable; downloaded Node receipts hash the official distribution tarball.

Fixtures contain an exact registry dependency, `is-number@7.0.0`. Generation writes and formats the package manifest before running the released manager. It never changes a lock's version number. Generation records the exact tool, Node, integrity, platform, arguments, source URL, resulting file hashes and output. Frozen installs run in a fresh temporary project with npm `ci`, pnpm `--frozen-shrinkwrap` before `3.0.0-alpha.3` and `--frozen-lockfile` from that version onward, Yarn Classic `--frozen-lockfile`, or Berry/native Yarn `--immutable`. Modern generation alone disables CI's implicit immutable mode. Current Modern fixtures use minimal PnP configuration that early Yarn 2 understands. The verifier loads the generated `.pnp.js` or `.pnp.cjs` with the exact test Node and resolves dependency manifests through it. It records `semanticMethod: pnp`; packages installed with a node_modules linker are read directly. Historical Yarn missing-node_modules failures without a PnP-aware receipt are not accepted as incompatibility evidence. Older `basic/` fixture bytes and measurements are retained; current `pnp/` recipes have new generation receipts and exact-generator frozen passes. Lifecycle scripts are disabled. Each run checks all committed fixture-input bytes and the actual installed dependency package versions, not just exit status. An exit-zero rewrite or wrong/missing installed dependency is maintenance-required.

Install stores are scoped to each temporary project. The runner supplies the historical `npm_config_store`, `npm_config_store_path` and `pnpm_store_path` aliases as well as `npm_config_store_dir`, because older pnpm releases read different configuration keys. Official-source receipts and production probes for pnpm 0.60, 0.65 and 2.17 are archived in `evidence/pnpm-store-isolation/`.

Network errors, unsupported execution environments, timeouts and unrecognized process failures are inconclusive. Recognized frozen-lock rejections are incompatible. Original stdout/stderr, command, before/after hashes, installed versions and composite identity remain in append-only observations/logs. Reruns reuse conclusive results only for the same fixture bytes, exact manager/integrity, exact Node/integrity, and platform/architecture. Old records are never overwritten. Archived fixture-input bytes are stored in `evidence/fixture-archives` when a generation-input formatting change requires a new fixture hash.

## Evidence and ranges

Before updating data, inventory the whole matrix with `pnpm data:audit --report PATH/report.json --json PATH/gaps.json --markdown PATH/gaps.md`. Inspect every internal stable gap, uncompiled supported point and contradiction. The inventory distinguishes unknown experiments already inside a range from versions actually excluded by the range. Record the cause and disposition of every gap; fixing one reported version does not complete the audit. The [complete initial audit](evidence/gap-audit/README.md) retains the before/after inventories and per-manager evidence.

For each discontinuity, reproduce the raw failure, inspect the official reader and release history, and compare the frozen control. Installer bugs need exact known-bug reviews; wrong commands/settings or missed explicit errors need runner fixes and new measurements. Preserve deliberate format/cache migrations. Missing archives, broken startup, wrong version labels and runtime failures remain unknown unless a valid experiment resolves them. pnpm format tests align the lock's boolean `autoInstallPeers` and `excludeLinksFromLockfile` settings; record that environment and use the same settings in controls and paired boundaries.

Twenty-three real fixture recipes exist: npm package-lock and shrinkwrap v1/v2/v3; pnpm legacy shrinkwrap 3/4 and lockfile 5/5.1/5.2/5.3/5.4/6/9; Yarn Classic v1 and Modern 4/5/6/7/8/9/10. The legacy pnpm v4 case covers the root dependency in shared-workspace mode. Its recipe generates both `.npmrc` and `pnpm-workspace.yaml`; the generation-only option is `--shared-workspace-shrinkwrap` before `3.0.0-alpha.3` and `--shared-workspace-lockfile` afterward. Generation and frozen-install options are separate. See `fixtures/README.md` for coverage and limitations.

`data:compile` compiles the full initial matrix; see [compile-initial.md](compile-initial.md) for its algorithm and paired boundary retests. Supply every evidence directory together with its original catalog. The current catalog determines release adjacency; older observations are reused only if their original catalog identifies the same immutable distribution and their fixture/protocol match. An expanded catalog never rewrites prior evidence.

Unsupported→supported opens an inclusive lower bound; supported→unsupported closes an exclusive upper bound; restored support adds an OR interval. Opposite outcomes must be catalog-adjacent stable releases measured with the same fixture, Node integrity, architecture and platform. Retest tasks identify missing or incomparable boundaries. No upper bound is invented from the last passing test. An unknown or unconfirmed format remains `*`. Open upper bounds describe the approved optimistic inference policy for older package releases; they do not claim future versions were tested. Automatic catalogs, maintenance statistics, fixture generation, test matrices and compiled compatibility ranges include stable versions only. Historical prerelease observations and generated fixtures remain archived unchanged.

`compile-compatibility.ts` and `boundaries.json` remain available for explicitly selected boundary pairs. The packaged data contains only compiled rules and compact known-bug markers; raw tools, catalogs and installation logs remain maintenance evidence.

## Release checks and persistence

The scheduled workflow uses `--incremental` and restores the dedicated `compatibility-data` evidence branch. It checks only exact released artifacts without a recorded terminal result, including new stable patches on old branches. A replaced official artifact is new work even when its version string is unchanged. A recipe or rule change alone does not automatically rerun a recorded release.

On first use, the monitor imports the initial matrices' attempts, including failed and inconclusive rows. Every current recipe must have a recorded attempt before an imported release is considered checked. Artifact identities and fixture hashes must match; original rows and logs are copied into the evidence branch. These scheduling records are separate from conclusive compatibility facts: an inconclusive attempt is never turned into supported or incompatible evidence.

Earlier release-check results migrate only when the saved catalog and terminal report agree; a start timestamp alone is never proof of completion. Each newly selected release runs format discovery and frozen-install checks. Its terminal result, raw outcomes and evidence links are written to an immutable `checks/` receipt and indexed in `state.json`. `history.json` and `history.md` retain the per-release results. Previous reports are archived under `reports/`; explicit retries keep separate generation directories and immutable result receipts. The next daily run reuses the recorded result, including failures, instead of retrying it. Starting an attempt alone does not count as finishing it; interrupted unrecorded work stays pending. New failures still return 1 (maintenance required) or 2 (incomplete), while a run with no new work returns 0. Historical unresolved items stay visible in the report without failing unrelated daily checks.

The batch limit applies only to pending new work; overflow remains pending for the next run. Use the workflow's `retry_failed` input or `--incremental --retry-failed` for an explicit retry. For a strict historical audit that re-evaluates coverage and unresolved findings, omit `--incremental`. Discovery uses exact artifact sets, never a highest-version watermark.

JSON/Markdown reports, the exact catalog, generated candidates, state, observation records and logs are written before failure. Workflow artifacts upload before the final failing step, and evidence is saved even on exit 1 or 2. The workflow does not publish npm packages.

## Historical tools and monitoring policy

Provisioning accepts `ProvisionOptions` as its sixth argument: `cacheDirectory`, `nodeArch`, `timeoutMs`, `historicalNode`, and opt-in `bootstrapDependencies`. Generation accepts the same options as its fourth argument. The official archive cache prevents downloading the same Node distribution for every manager version; extraction is shared by version, platform, architecture and verified archive checksum. Local cached binary stamps are verified before reuse. Both archive operations and exact-version/architecture commands have bounded timeouts.

Historical selection uses published Node dates plus the manager's declared engines. It chooses a stable Node available by the manager's release date, rather than treating a broad old `>=` engine as proof that an ancient manager runs on today's Node. A missing release date falls back to normal compatible selection; absent historical candidates or unavailable platform binaries remain incomplete. `nodeArch: 'x64'` supports old official macOS distributions via Rosetta, with actual executable architecture recorded separately from host architecture.

Some old official manager tarballs omit their runtime dependencies. Only explicit `bootstrapDependencies: true` enables a fallback after a missing-module startup error. It invokes the npm adjacent to the current Node in an isolated tool copy, installs production dependencies from the official registry with lifecycle scripts disabled, saves the exact generated dependency lock and hash plus command/output, then retries the exact old manager under the selected historical Node. The original official tarball is never modified. `Tool.bootstrap` and each resulting observation distinguish original tool integrity from the resolved production dependency graph; observation identities and reuse include its lock SHA. Bootstrap requires a persistent cache directory so the controller can preserve these records in source/evidence storage. Failures retain their logs and remain incomplete.

Routine monitoring compares unchanged fixtures against comparable actual observations even when no range has been compiled. Unestablished behavior is visible maintenance work, never a fabricated runtime restriction. Prerelease releases and their archived observations do not enter monitoring queues, counts or behavior comparisons. Daily incremental checks never automatically retry recorded failures. The strict audit and explicit retry modes retain the bounded retry lane for unfinished historical investigations.

npm rules also distinguish `match.file: package-lock.json` from `match.file: npm-shrinkwrap.json`. Equal numeric format versions do not prove equal behavior for these two file kinds. Initial full-version seeding is a separate operation. Coverage summaries distinguish attempted combinations, conclusive outcomes and unresolved execution failures; attempting every release does not mean every release can execute successfully.

## Positive controls and reviewed exclusions

The scheduled release check enables the same opt-in dependency bootstrap used by seeding for both tool provisioning and fixture generation. Downloads and prepared tools stay in `.cache/maintenance`; dependency locks and installer logs are copied into the evidence directory with relative paths before the runner is removed. A version probe that exits zero but reports no matching version still retains stderr and can trigger the missing-module bootstrap. Exact version verification is never bypassed. Operational errors retain their nested causes in `logs/failure-*.log`, and silent failed commands record their command and exit status. The workflow publishes `report.md` in its run summary as well as the artifact.

Every successful baseline also runs the recipe’s contradictory `controlDependencies` manifest under the same exact tool, Node and frozen command. The control must either explicitly reject the contradiction, or install the original locked versions with every watched input and lockfile unchanged. Silently installing the newly requested versions, rewriting files, or failing for an environmental/unknown reason makes the baseline inconclusive. Original fixture files remain unchanged; the nested `frozenControl` stores its own input hashes, requested dependencies, output and log. `data:seed` automatically rechecks old successful records missing the current control. Existing valid negative observations are retained.

When a reviewed measurement bug invalidates an observation, retain the original row and log and add a reasoned entry to that evidence directory’s `exclusions.json`: row ID, observation ID, SHA-256 of the original row bytes, review timestamp and reason. The compiler and release monitor validate this identity before excluding the row, preserve the audit record, and revoke completion if it depended on that evidence. Exclusions are not a way to hide actual package-manager behavior. Checksum errors alone, such as Yarn YN0018, remain inconclusive without evidence distinguishing a lock incompatibility from changed or corrupted archive bytes.

Generated output in `maintenance/evidence/` is excluded from ESLint; the evidence pipeline validates its JSON structure, recorded inputs, artifact identity and observation contract. Source code, configuration and fixture manifests remain linted. Formatting a current generation receipt does not change tested inputs; original receipt bytes are archived under `evidence/fixture-receipts-before-format/`.

Frozen installation uses each pnpm release’s historical option: `--frozen-shrinkwrap` before `3.0.0-alpha.3`, then `--frozen-lockfile`. The option is selected by the tested manager version for both lockfile names. An ignored option cannot establish support because the contradictory-manifest control must also pass.

## Semantic compatibility and known upstream bugs

Raw test failure and lock-format incompatibility are different facts. Use `known-bugs.json` for a reviewed upstream bug whose affected release is independently known to understand the format. Record the scope, official source, semantic evidence and exact failed observations. These observations remain failures in raw evidence but compile as compatible, with an explicit bug marker. A generator producing the same format is useful evidence, not an automatic blanket exception. The pnpm #6158 review covers preserved rewrites whose parsed YAML and installed dependencies remain unchanged; other bugs may fail differently and require their own review.

Never use a harness exclusion for this case: the test correctly recorded the installer bug. Exclusions invalidate a measurement; known-bug reviews retain the measurement and change only its compatibility interpretation. See [the compiler contract](compile-initial.md#reviewed-upstream-bugs). Only stable intervals are compiled in maintenance; full provenance stays here rather than in the npm artifact.

Explicit exact prerelease inputs remain a runtime feature, including an exact `packageManager` declaration in `package.json`; their release metadata is fetched on demand. Automatic selection of any unspecified version, including Node inferred from that manager, uses stable releases only. Maintenance does not provision prerelease tools or Node runtimes. Existing historical prerelease fixture recipes are retained and skipped during regeneration.

## Native Yarn

`repo.yarnpkg.com/releases` supplies the `releaseLines.zpm` version list. Merge its tags and channel values, then exclude SemVer prereleases. `runtime: native` means no host Node requirement; the project still receives a separately selected Node. Provisioning downloads the official platform npm package, checks its manifest/platform/SRI and binary version, and retains `NativeReceipt`. Linux uses the official static musl artifact on both musl and glibc hosts. Missing platform artifacts produce incomplete checks.

Native JSON `yarn.lock` files use `features.yarnFamily: zpm`; Berry YAML and native JSON can share a numeric metadata version. Discovery compares family and format, creates a distinct `yarn-zpm-vN` identity, and flags new formats for maintenance. Source inspection and a generator format do not establish frozen-install ranges. The first stable native release must be measured against the existing Yarn fixtures and its own generated fixture. Unknown native formats remain `*`; existing open Berry ranges remain unchanged until stable measurements establish a boundary.

The [Yarn 6 adapter verification](evidence/yarn6-integration/README.md) archives an explicitly selected RC with both node_modules and PnP, including contradictory-manifest controls. It verifies integration only and is excluded from active recipes, matrices, generated compatibility ranges, statistics and knownBugs.
