# English AI maintenance prompt

Maintain node-toolchain-infer using actual observed evidence. Work from main's code and fixtures plus the latest compatibility-data evidence artifact. Do not publish, push, create remote objects, install tools globally, hand-edit lock format numbers, or infer ranges from sparse passing samples. User authorization is required for remote writes outside an explicitly authorized workflow execution.

Official facts come from the Node release index, npm/pnpm/yarn/cli-dist/cli registry metadata, Yarn's Berry tag list, and `https://repo.yarnpkg.com/releases`. Historical Yarn standalone scripts may not exist in cli-dist. Pin their official tag to its peeled Git commit, download the script at that immutable commit, calculate and retain SHA-512/size, and verify the executable's reported version. Do not label a computed digest as registry-provided SRI or substitute a differently reported version. Preserve tag-only versions with missing engines as unknown. Expanding the catalog must not overwrite earlier snapshots or observations; `data:compile` accepts each evidence directory's original catalog and validates unchanged artifact identity before reuse.

For native Yarn 6+, union `releaseLines.zpm.tags`, `stable` and `canary`; filter by the actual SemVer version, even when a channel called stable points to an RC. Native metadata uses `runtime: 'native'` and host Node constraint `*`, not an invented engines declaration. Use the official `@yarnpkg/yarn-<platform>` npm artifact directly, validate manifest identity/platform/SRI and actual executable version, and retain the binary digest. Missing platform artifacts are incomplete. Do not hydrate native versions through Berry bundles or bootstrap dependencies. Classify lock contents before looking up format numbers: native JSON uses `features.yarnFamily: 'zpm'`; Berry YAML rules with the same number do not apply. New native formats remain unknown `*` until stable-version measurements establish rules; do not close existing open Berry intervals merely because the runtime implementation changed. A deliberately requested RC integration check can be archived separately to verify the adapter, but never enters fixture recipes, compatibility matrices, range compilation, release statistics or knownBugs.

Every current fixture must provide `controlDependencies`. A successful baseline is accepted only if the same frozen command, lock bytes, exact tool and Node either explicitly reject a contradictory manifest or install the original locked versions without changing any watched input or lockfile. Silently installing the newly requested versions does not qualify. Preserve nested control receipts and logs. For a proven harness bug, preserve the original row and add a reviewed SHA-256-bound `exclusions.json` entry; never relabel an old result silently.

1. Read maintenance/README.md, fixtures/README.md, data/compatibility.json, boundaries.json, report.json, report.md and state.json. Preserve every old observation and every in-scope unresolved item. Report the exact observed failure before proposing a change.
2. Fetch all official release metadata with `pnpm data:sync --output maintenance/results/catalog.json`. Compare exact version sets, including stable patch releases on old branches; exclude prereleases. Inspect official tarball SRI, package manifest, engines.node, source URL and release timestamp. Never substitute a third-party guessed compatibility table.
3. Reproduce the same failing command: `pnpm releases:check --state-dir maintenance/results --max-releases 8`, or its report-supplied `--catalog` snapshot. Keep JSON/Markdown/logs on failure. Distinguish code0 success, code1 maintenance-required and code2 incomplete. Code2 must preserve any simultaneous code1 findings.
4. For a new format or feature, create a recipe with a real nonempty dependency graph and an appropriate released manager. Generate it with the checked official tarball and compatible exact Node. Format the input manifest before generation. Preserve generator output, hashes, integrity, exact arguments and logs. Never patch only the lockfileVersion/metadata number. Archive prior fixture bytes when replacing a recipe input.
5. Inspect official tool source/release notes to explain the behavior and identify candidate transition releases. Then measure both adjacent published stable sides against the identical fixture/Node/platform: `pnpm compat:test --fixture FIXTURE --versions MANAGER@BEFORE,MANAGER@AFTER --catalog maintenance/results/catalog.json`. Confirm actual installed dependency versions and unchanged lock/manifest bytes. Use the frozen option that existed in the tested release: pnpm before `3.0.0-alpha.3` uses `--frozen-shrinkwrap`, later versions use `--frozen-lockfile`. Verify command support rather than assuming an ignored unknown option is valid. Frozen rejection is incompatible; network/engine/process failures are inconclusive and cannot establish a bound.
6. Add only confirmed adjacent opposite-outcome receipt IDs to maintenance/boundaries.json. Compile with `pnpm exec tsx maintenance/compile-compatibility.ts --catalog maintenance/results/catalog.json`. Inclusive lower, exclusive upper, restored OR intervals; leave the final upper end open. Unknown formats remain `*`. A successful maximum tested version does not justify an upper bound. If the catalog is filtered, fetch the complete official catalog before claiming adjacency.
7. Update parsers/recipes/rules/docs/tests to cover the observed case. Re-run exactly the failing command against preserved state, then targeted tests, typecheck and lint. Unresolved items stay red until the evidence plus changed code/rules actually resolve them. Do not delete state to get green. Report source changes, measured versions, receipt IDs, before/after status and remaining gaps. Keep source changes separate from append-only workflow data. No automatic npm publish.

Separate the raw test outcome from semantic lock-format compatibility. A manager may support or generate the format while a known upstream bug fails its installer test. Establish that support and the failure cause independently, then register a review in `maintenance/known-bugs.json`: bug source, affected manager/version range/fixtures, semantic evidence, review date, and exact failed observation IDs with `observationFingerprint` values. Retain every original status and output. Only matched reviewed evidence becomes compatible; unrelated failures remain unresolved. This applies beyond formatting-only rewrites. Use harness exclusions only when the measurement itself was wrong. Compile with `pnpm data:compile` and all original evidence directories plus the known-bug reviews; preserve report exception markers and ship compact markers, not full provenance. Compile only stable versions into ranges. Exclude prereleases from ordinary metadata lists, statistics, generation, test matrices, monitoring and reports. Preserve archived prerelease evidence unchanged. Explicit runtime versions and ranges (including package.json packageManager) fetch matching prerelease metadata on demand using standard semver matching. This applies only to the declared tool; inferred Node needs its own explicit declaration to admit prereleases. These on-demand records never enter the maintained compatibility data.

Before concluding a gap investigation, run `pnpm data:audit` on the full before/after compiler reports. Account for every stable internal gap, not just the user's examples. Distinguish semver membership, semantic compatibility and raw installation status. Explain the preserved real boundaries and every remaining unknown; attach exact rows, logs, source links and controlled reproductions. Rebuild the bundled table and calculator only after reviewing the full inventory. Keep confirmed historical facts; local experiment reuse and adjacent-version comparisons must use the same explicit installation environment. A parser/classifier fix requires rerunning every affected point in the audited gap, rather than only registering a bug or changing an old status.

# 中文 AI 维护提示词

请基于真实行为证据维护 node-toolchain-infer。代码和样例取自主分支，历史证据取自 compatibility-data 分支或最近的工作流制品。不要发布 npm 包、推送远端、创建远端对象、全局安装工具、手工修改锁格式数字，也不要用稀疏成功点猜版本范围。除已明确授权执行的工作流外，远端写操作需要用户授权。

官方事实取自 Node 发行索引，npm/pnpm/yarn/cli-dist/cli 注册表、Yarn 官方 Berry tag 列表以及 `https://repo.yarnpkg.com/releases`。历史 Yarn 独立脚本不一定在 cli-dist 发布：将官方 tag 解引用到 Git commit，从该不可变 commit 下载脚本，计算并保存 SHA-512、大小，核对命令实际自报版本。不得将自己计算的摘要说成注册表提供的 SRI，也不得用其他自报版本冒充目标版本。只有 tag、缺失 engines 的版本保持未知。扩充清单不得覆写旧快照或记录；`data:compile` 读取每个证据目录的原清单，核实制品身份相同后复用旧实验。

原生 Yarn 6+ 的版本取 `releaseLines.zpm.tags`、`stable`、`canary` 的并集；以 SemVer 版本号判断稳定性，不能因为渠道名叫 stable 就纳入 RC。原生元数据使用 `runtime: 'native'` 和宿主 Node 约束 `*`，不伪造 engines 声明。直接运行官方 `@yarnpkg/yarn-<平台>` npm 制品，校验包身份、平台、SRI 和程序自报版本，保存二进制摘要；缺少平台制品时标记检查不完整。不得用 Berry bundle 或依赖 bootstrap 替代原生程序。先识别锁文件内容类型，再查询格式号：原生 JSON 带 `features.yarnFamily: 'zpm'`，不能命中同号 Berry YAML 规则。没有稳定版实测规则的新格式保持未知 `*`，也不能因为 Yarn 改用原生程序就关闭已有 Berry 区间。为验证接入而明确运行的 RC 检查单独归档，不进入样例 recipe、兼容矩阵、范围编译、版本统计或 knownBugs。

每份当前样例必须配置 `controlDependencies`。成功案例还必须在同一精确工具、Node、锁文件和冻结命令下运行矛盾清单对照：明确拒绝矛盾清单，或仍安装原锁定版本且所有监测文件字节不变，才算有效；静默安装清单中新要求的版本不算。保存嵌套对照记录与日志。确认测试程序存在误判时，保留原记录，追加带原记录 SHA-256、理由与复核时间的 `exclusions.json` 条目，不得悄悄改写旧结论。

1. 阅读 maintenance/README.md、fixtures/README.md、data/compatibility.json、boundaries.json、report.json、report.md 与 state.json。保留全部旧记录和未解决项，先说明实际失败行为，再提出修改。
2. 使用 `pnpm data:sync --output maintenance/results/catalog.json` 获取完整官方目录。按精确版本集合比较，包含旧主版本的新稳定补丁，排除预发布版。核实官方 tarball 完整性、包清单、engines.node、来源 URL 和发布时间，不采用第三方猜测表。
3. 使用原命令 `pnpm releases:check --state-dir maintenance/results --max-releases 8`，或报告附带的 `--catalog` 快照复现。失败时仍保存 JSON、Markdown 与日志。退出码0表示完成，1表示需要维护，2表示检查不完整；出现2时也必须保留同时发现的维护问题。
4. 出现新格式或新特性时，用真实非空依赖关系创建 recipe，使用已发布的精确工具版本生成；校验官方 tarball 和兼容的精确 Node。先规范输入 package.json 格式，再生成锁文件。保存生成器输出、文件哈希、完整性、实际参数和日志。禁止只改 lockfileVersion 或 metadata 数字；替换样例输入时归档原始字节。
5. 查阅官方源码和发布说明，解释行为并确定候选边界。使用同一份样例、同一 Node 和平台测相邻的两个已发布稳定版本：`pnpm compat:test --fixture FIXTURE --versions MANAGER@BEFORE,MANAGER@AFTER --catalog maintenance/results/catalog.json`。确认依赖实际安装版本正确，锁文件和清单字节不变。pnpm 早于 `3.0.0-alpha.3` 使用 `--frozen-shrinkwrap`，从该版本起使用 `--frozen-lockfile`；核实待测版本支持的命令，不得将忽略未知选项当作有效冻结安装。冻结拒绝才算不兼容；网络、引擎或进程异常是不确定，不能作为边界。
6. 仅将已经确认、相邻且行为相反的记录 ID 写入 maintenance/boundaries.json，再运行 `pnpm exec tsx maintenance/compile-compatibility.ts --catalog maintenance/results/catalog.json`。下界包含、上界不包含；恢复支持生成 OR 区间；最后一段保持开放上界。未知格式维持 `*`。最后一次成功的版本不能当作上界；裁剪过的目录不能证明版本相邻。
7. 更新与实际问题对应的解析器、recipe、规则、文档和测试。对保留的状态重新运行原失败命令，然后执行针对性测试、类型检查与 lint。未解决问题必须持续红灯，直到新代码/规则和证据共同证明已解决，不能删除状态来变绿。报告修改内容、实测版本、记录 ID、前后结果以及覆盖缺口。源码修改与工作流追加数据分别保存，不自动发布 npm。

将原始测试结果与锁格式的语义兼容性分开。某版本可以支持甚至生成该格式，但因已知上游 bug 未通过安装测试。独立确认格式支持和失败原因后，在 `maintenance/known-bugs.json` 登记 bug 来源、受影响包管理器/版本范围/样例、语义依据、审核时间、失败记录 ID 及 `observationFingerprint`。原始状态与输出一律保留；只将精确匹配的审核记录按兼容处理，其他失败继续调查。例外不限于格式重写。测试程序本身误测才使用 exclusions。通过 `pnpm data:compile` 加载全部原证据目录和已知 bug 审核记录；维护报告保留例外标记，发行包只保留精简标记，不携带完整 provenance。只将稳定版本编译为范围。普通元数据列表、统计、样例生成、测试矩阵、监控和报告全部排除预发布版，归档的原始预发布证据保持不变。运行时显式指定的精确版本和范围（含 package.json 的 packageManager）按标准 semver 匹配，按需获取符合声明的预发布元数据，且只对被声明的工具生效；推导出的 Node 需要自己的显式声明允许，才可采用预发布版。这些按需查询的记录不加入维护数据。

断点核查结束前，对完整的修改前后编译报告运行 `pnpm data:audit`。逐项解释全部稳定版内部缺口，不只处理用户举出的版本。分清 semver 是否包含、语义兼容与原始安装结果；说明保留的真实边界和每项未知原因，附原始记录、日志、官方来源和控制实验。复核整份清单后再更新随包数据与计算器。历史已确认事实继续保留；复用本地实验或比较相邻版本时，显式安装环境必须一致。修正解析器或错误分类后，要补跑该断点涉及的全部版本，不能只登记一个 bug，也不能改写旧状态。
